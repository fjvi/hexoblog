测试标题

Created2026-10-01|Updated2026-10-01

根据你提供的仓库信息，这是一个标准的 Hexo 博客项目（包含 _config.butterfly.yml 和 source/_posts 结构）。要实现 Issue → 静态页面 → 新分支 → Cloudflare Pages 的自动化闭环，可以拆解为三步。

  1. 编写 GitHub Actions 自动化脚本

你需要在 .github/workflows/ 下新建一个 sync-issues.yml。脚本逻辑是：拉取 Issue 内容，通过 Hexo 渲染成静态页面，最后推送到 gh-pages 分支。

关键点：

· 避免无限循环：推送 gh-pages 不要触发 on: push，否则 Actions 会自己循环触发自己。
· 模板适配：脚本里的 frontMatter 需要根据你 scaffolds/post.md 的格式调整（比如是否有分类、封面等字段）。

  1. 配置 Cloudflare Pages

gh-pages 分支有了静态内容后，就可以让 Cloudflare 来“克隆”部署了：

  1. 登录 Cloudflare Dashboard，进入 Workers & Pages。
  2. 点击 Create application → Pages → Connect to Git。
  3. 选择你的仓库 fjvi/hexoblog。
  4. 关键设置：
    · Production branch：选择 gh-pages（不要选 main）。
    · Build command：留空（因为 gh-pages 里已经是构建好的 HTML）。
    · Build output directory：填 / 或留空。
  5. 点击 Save and Deploy。

为什么这样配置？
Cloudflare Pages 默认从指定分支拉取代码，如果检测到构建命令为空，它会直接托管该分支下的静态文件。这样你的 Hexo 源码和部署产物就完全解耦了。

  1. 注意事项

· 草稿隐私：你的仓库是公开的，请勿在 Issue 中写私密信息，因为 Issue 本身也是公开的。
· 图片处理：Issue 中的图片链接通常是 github.com/user-attachments/…，直接放到 Hexo 里可能无法显示。建议在脚本中增加一步，自动下载图片到 source/images/ 并替换链接。
· 标签控制：如果你希望只有特定 Label（例如 publish）的 Issue 才发布，在 on 触发器里可以不用变，但在脚本里加判断：if (!issue.labels.some(l => l.name === ‘publish’)) return;。

这样，你平时只需要在 GitHub 上写 Issue，打上 publish 标签，Actions 就会自动生成页面并推送到 gh-pages，Cloudflare Pages 检测到变化后会自动重新部署。
